# InsightForge 技术复盘

## 最重要的架构决定

项目没有把 Agent 当成一次同步 HTTP 调用。企业调研包含搜索、抓取、生成、评审和可能的修订，执行时间与失败点都不可预测，因此 Web 只入队，Worker 独立运行，数据库保存权威状态，Redis 保存短期事件，LangGraph Checkpoint 保存节点恢复位置。

## 复杂度来自哪里

真正困难的部分不是调用模型，而是副作用一致性：证据已写入但 checkpoint 未提交时怎么办，报告发布后进程退出怎么办，Worker 重试是否重复搜索。解决方式是稳定 ID、唯一约束、不可变版本、先保存事件再 Pub/Sub，以及恢复时从数据库重新读取身份和结果。

## RAG 的认识变化

向量检索只是候选召回的一部分。企业名、产品名和财务术语很依赖精确关键词，因此项目同时使用全文检索与向量检索，再用 RRF 融合。任何排序优化都必须回到 Golden Dataset，而不是凭几个聊天示例判断。

## Agent 质量不是一个分数

检索需要 Recall/MRR，报告需要引用覆盖与支持度，运行需要成功率、延迟、成本和恢复行为。确定性校验适合身份、引用存在性、章节和预算；模型 Reviewer 只处理语义支持与表达质量。把两者混为一个“LLM 评分”会降低可解释性。

## 当前限制与后续方向

- 公开创建页的上传时序仍需预上传会话或延迟入队协议；
- Worker 进度事件尚未覆盖每个 Graph 节点；
- 扫描 PDF 没有 OCR；
- 夹具评测不能替代真实供应商在线评测；
- 第一版 Worker 单副本运行，扩容前需要验证供应商限额、数据库连接预算和队列并发。
